# SRE Module Refactor: Cycle Length Handling and Block-Based Vector Construction

## Overview

The SRE module underwent a critical refactor to properly handle cycle length variants and ensure consistent vector construction within timing sequence blocks. The core insight is that **vector length (tseq) must be determined once per timing_sequence block, not per individual row or per variant**. This prevents shape mismatches when mapping cycle lengths to generated regimen strings.

## The Problem Being Solved

Prior implementation had a fundamental mismatch: when a single drug had multiple cycle length variants (where cycle_length_lb ≠ cycle_length_ub), the pipeline would create multiple component vectors but lose track of which vector belonged to which cycle length and timing sequence. This caused two critical failures:

**Failure 1: Shape Error in Polars DataFrame**  
The system attempted to add a column of mismatched length. For example, a group with 320 rows would receive cycle_length values of count 100 (the number of generated regimen strings), creating an incompatible shape for concatenation.

**Failure 2: Lost Cycle Length Mapping**  
When multiple regimen strings were generated from variant combinations, the cycle_length output values didn't correspond correctly to which variant produced which regimen string.

The refactor eliminates both issues by establishing a clear ownership model: each timing_sequence block owns one authoritative vector length (tseq), and all variants within that block use that same tseq.

## Key Concept: tseq (Timing Sequence Length)

**tseq** represents the authoritative cycle length in days for a given timing_sequence block. It is computed as:

tseq = max(  
  maximum day mentioned in allDays across all rows in the block,  
  maximum cycle_length metadata value (lb or ub) converted to days across all rows in the block  
)

This ensures the vector is long enough to accommodate all administration days and respect the cycle length metadata boundaries.

## Architecture Changes

### 1. New Function: `_infer_block_tseq()`

This function computes the authoritative tseq for a timing_sequence block by examining all rows in the block simultaneously. It iterates through each row and extracts:

- allDays: Parsed into individual day integers (idays). The maximum day value is noted.
- cycle_length_lb and cycle_length_ub: Converted from their unit (day, week, month, indeterminate) into days using `convert_to_days()`. The maximum of these bounds is noted.

The function returns the maximum across both sources. This is crucial because the vector must be long enough for both the actual drug administration days and the declared cycle length.

**Why block-level computation?** Because rows with the same timing_sequence value share a common cycle context. A timing_sequence represents "which regimen cycles is this component active in" (e.g., cycles 1, 3, 4). All components active in those same cycles must have vectors of the same length to align properly in the event matrix.

### 2. Refactored Function: `_build_vector_from_idays()`

Previously, this function computed its own vector length. Now it accepts tseq as a parameter. This ensures all variants (different cycle_length values) for the same drug in the same timing_sequence produce vectors of identical length. The function builds a binary vector of length tseq with 1s at positions specified by idays (parsed day offsets).

### 3. Rewritten Method: `_process_group()`

The group processing now follows a structured two-level hierarchy:

**Level 1: Timing Sequence Grouping**  
The group (defined by regimen_cui, variant_cui, condition_cui) is first subdivided by timing_sequence. For each timing_sequence value, a block is extracted. The block contains all rows with that timing_sequence, which may represent different components or the same component with different idays/cycle_length values.

**Level 2: Row and Variant Processing**  
Within each block:

1. Compute tseq = _infer_block_tseq(block)
2. Store this mapping: timing_seq_to_tseq[timing_seq] = tseq
3. For each row in the block:
   - Extract the drug name
   - Parse idays from allDays
   - Create a SET from {cycle_length_lb, cycle_length_ub}. If lb equals ub, the set has one element. If they differ, two separate variants are created.
   - For each cycle_length value in the set:
     - Build a vector using the block's tseq (not the cycle_length value)
     - Append (timing_seq, vec) to component_vectors[drug]

This approach ensures that **multiple variants of the same drug get appended as separate entries in the component_vectors list, but all share the same vector length (the block's tseq)**.

### 4. Cycle Length Output Mapping

After regimen strings are generated by `create_reg_string()`, the number of regimen strings produced equals the number of unique variant combinations. For each regimen string, a cycle length must be assigned.

The refactored approach:

1. Collect all tseq values from all timing_sequences in the group: tseqs = list(timing_seq_to_tseq.values())
2. Use the maximum: cycle_length = max(tseqs) if tseqs else 1
3. Create an array of this value repeated len(reg_strings) times
4. This ensures the cycle_length column has exactly the right count to match regimen strings

**Why use max?** If a group spans multiple timing_sequences with different tseq values, the output regimen string must fit the longest cycle to avoid truncation. Using max(tseqs) ensures all generated strings are valid for the complete group context.

## Three Types of Variants

The refactored system unifies handling of three variant generation mechanisms:

### Variant Type 1: Cycle Length Variants (lb vs ub)

When cycle_length_lb ≠ cycle_length_ub for a single row, the system creates two variants by splitting the set {lb, ub}. Both variants produce vectors of the same length (block's tseq) but may participate differently in event matrix construction depending on downstream logic.

**Example:**  
Row: component=Paclitaxel, idays=[1,8], cycle_length_lb=21, cycle_length_ub=28

Set created: {21.0, 28.0}

Two vectors are generated:
- Vec1: length = tseq, marks days 1 and 8
- Vec2: length = tseq, marks days 1 and 8

Both are appended to component_vectors["Paclitaxel"] with the same timing_seq tag.

### Variant Type 2: Vector Length Variants (@cycleLen suffixes)

Handled by `normalize_multicycle_spans()` in sre_tools. When a component has different idays patterns across rows within a block, the system creates separate @cycleLen{L} keys (where L is the vector length). These are later stripped in `collapse_event_matrix()` to produce clean output.

### Variant Type 3: Timing Sequence Variants

The same drug may appear in different timing_sequences (different regimen cycles). These are tracked separately by the timing_seq key in the component_vectors tuples. Each timing_sequence has its own tseq, so vectors have different lengths across timing_sequences.

**The refactored system treats all three mechanisms uniformly**: each produces multiple entries in the component_vectors list, and `create_reg_string()` (which calls the normalize→validate→pad→collapse pipeline) handles merging them into final regimen strings.

## Data Structure: component_vectors

component_vectors is a dictionary mapping drug names to lists of tuples:

```
component_vectors: Dict[str, List[Tuple[timing_seq, np.ndarray]]]
```

Example structure after processing:

```
{
  "Paclitaxel": [
    (1, [1, 0, 0, 1, ...]),     # timing_seq 1, variant from lb
    (1, [1, 0, 0, 1, ...]),     # timing_seq 1, variant from ub
    (2, [0, 1, 0, 1, ...]),     # timing_seq 2, same component different timing_seq
  ],
  "Carboplatin": [
    (1, [0, 1, 0, 0, ...]),     # timing_seq 1
    (2, [1, 0, 0, 0, ...]),     # timing_seq 2
  ]
}
```

All tuples with the same timing_seq value have vectors of the same length (the tseq for that timing_seq). Tuples with different timing_seq values may have different vector lengths.

## Example: Multi-Timing-Sequence Group

Consider a group spanning two timing_sequences with different cycle lengths:

**Timing Sequence 1: cycles 1, 2, 3 (21-day cycles)**

| component | allDays | cycle_length_lb | cycle_length_ub | cycle_length_unit |
|-----------|---------|-----------------|-----------------|-------------------|
| Paclitaxel| 1, 8    | 21              | 21              | day               |
| Carboplatin| 1       | 21              | 21              | day               |

tseq for block 1 = max(8, 21) = 21

**Timing Sequence 2: cycles 4, 5 (28-day cycles)**

| component | allDays | cycle_length_lb | cycle_length_ub | cycle_length_unit |
|-----------|---------|-----------------|-----------------|-------------------|
| Paclitaxel| 1, 8    | 28              | 28              | day               |
| Carboplatin| 1       | 28              | 28              | day               |

tseq for block 2 = max(8, 28) = 28

**Processing:**

Block 1 iteration:
- Paclitaxel creates one variant (lb = ub = 21) → vector of length 21
- Carboplatin creates one variant → vector of length 21
- Both appended with timing_seq=1

Block 2 iteration:
- Paclitaxel creates one variant → vector of length 28
- Carboplatin creates one variant → vector of length 28
- Both appended with timing_seq=2

**Output cycle length:** max(21, 28) = 28

This output cycle length forms the row dimension of the event matrix. The LA (linear algebra) layer then calculates drug administration distances and patterns while respecting the different cycle lengths across timing sequences. By using max(tseqs), the matrix accommodates the longest cycle, ensuring all drug vectors are properly aligned for downstream distance calculations.

## Critical Guarantees

1. **Vector Length Consistency**: All vectors within a timing_sequence block have the same length (tseq).

2. **Count Matching**: The number of cycle_length values in the output exactly matches the number of regimen strings generated. Both equal len(reg_strings).

3. **Variant Tracking**: Each variant (from lb/ub split, vector length difference, or timing_sequence difference) creates a separate entry in component_vectors, allowing `create_reg_string()` to generate the correct number of unique output strings.

4. **No Data Loss**: The timing_seq key in each tuple allows the collapse phase to track which variants belong to which timing contexts, preventing merging errors.

## Testing and Validation

The refactor was validated against the test case `test_collapse_event_matrix_wrapper_esv_cases`, which specifically tests the esv5 case: a component (Cy) with two variants (len5 and len10) in the same timing_sequence. The corrected system now:

- Generates two separate component vectors for Cy
- Produces two separate regimen strings (one per variant)
- Maps two corresponding cycle_length values
- Successfully merges outputs without shape errors

All unit tests in src/tests pass (6/6), confirming backward compatibility and correctness of the variant handling mechanism.
